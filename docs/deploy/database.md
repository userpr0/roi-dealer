# База данных в облаке (PostgreSQL в Railway)

> Подготовлено в PHASE 02. **Создавать облачную БД сейчас не обязательно:** в PHASE 02 ей ещё некому пользоваться (бот не хранит данных, api не развёрнут). Рекомендуемый момент — вместе с 13b, когда бот начнёт сохранять одобрения. Тогда Claude проверит шаги ниже на месте и уточнит инструкцию.
> Интерфейс Railway меняется: если кнопка называется иначе, ищите ближайшую по смыслу.

## Сколько стоит

Railway берёт деньги за фактически использованные память, CPU и диск. Небольшая PostgreSQL без нагрузки обычно укладывается в несколько долларов в месяц; вместе с ботом это должно помещаться в лимит инфраструктуры $20/мес (D-007). Лимиты расходов в Railway уже стоят ($15 — письмо, $20 — остановка), см. [`owner-setup.md`](owner-setup.md).

## 1. Создать базу (5 минут)

1. [railway.com/dashboard](https://railway.com/dashboard) → проект с ботом → на поле **+ Create** (или **+ New**) → **Database** → **PostgreSQL**.
2. Дождитесь, пока карточка **Postgres** станет **Online**.
3. Версия: откройте карточку → **Deployments** → **View logs** и найдите строку `PostgreSQL 18…`. Миграции проверены на PostgreSQL 18, как локально и в CI. Если Railway создал другую версию, напишите Claude до подключения сервисов.
4. **Settings** → **Networking**: публичный адрес (**TCP Proxy**) не включайте. Сервисы проекта подключаются по внутренней сети Railway.

## 2. Подключить сервис

У сервиса, которому нужна БД (с 13b — бот), откройте **Variables** → **+ New Variable**:

| Переменная     | Значение                     |
| -------------- | ---------------------------- |
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` |

Это ссылка на переменную сервиса Postgres: пароль не копируется руками и не попадает в чат. Затем **Deploy**.

## 3. Миграции

Миграции применяет команда `pnpm db:migrate` (раннер `@roi-dealer/database`). В облаке её запускает отдельный шаг деплоя перед стартом новой версии сервиса. Этот шаг Claude добавит в 13b вместе с первым облачным потребителем БД: сейчас в Docker-образе бота нет ни миграций, ни раннера.

Запускать одновременно несколько копий раннера безопасно: вторая ждёт блокировку и пропускает уже применённые файлы.

## 4. Резервные копии

Два уровня:

1. **Копии диска у Railway.** Карточка **Postgres** → вкладка **Backups** (если есть на вашем тарифе) → включите ежедневные копии. Восстановление — там же, **Restore** выбранной копии. Наличие вкладки и расписания проверяются при создании БД.
2. **Логическая копия `pg_dump`** — не зависит от Railway: из неё базу можно поднять у любого провайдера или локально. Делается по запросу владельца или по расписанию, которое Claude настроит в 13b. Для этого нужен публичный адрес БД, поэтому он включается только на время копирования.

Восстановление логической копии в новую пустую базу:

```bash
pg_restore --no-owner --dbname "$NEW_DATABASE_URL" roi-dealer-YYYY-MM-DD.dump
```

После восстановления `pnpm db:migrate` проверит, что журнал миграций совпадает с кодом, и применит недостающие файлы.

## 5. Staging (D-014 п.3)

Для проверок без риска для рабочих данных: в Railway **Environments** → **+ New Environment** `staging` с отдельной PostgreSQL и тестовым ботом (своим `TELEGRAM_BOT_TOKEN`). Создаётся вместе с 13b.

## Безопасность

- `DATABASE_URL` содержит пароль: только в переменных Railway (ссылкой) или в локальном `.env`. Логгер его редактирует.
- Сервисы подключаются по внутренней сети; публичный адрес не включается без необходимости.
- Утечка пароля БД: сразу выключите публичный адрес (**TCP Proxy**), если он был включён, и напишите Claude. Пароль меняется SQL-командой `ALTER ROLE … PASSWORD` вместе с переменными Railway; одна смена переменной в интерфейсе пароль внутри базы не меняет. Общий порядок — [runbook](../runbooks/secret-leak.md#другие-ключи).
