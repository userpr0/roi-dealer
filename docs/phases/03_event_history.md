# PHASE 03 — Event History

> **Основание:** playbook v1.1 §7 («append-only event store, audit, idempotency»), §2.2 Event History, §2.11 (audit logs), §2.13; [план пульта](13_owner_command_center.plan.md) (журнал и история за день / неделю / месяц, повторное нажатие не выполняет действие дважды, аудит с `correlation_id`); решения владельца D-002, D-010, D-016.
> Спецификацию составил Claude по поручению владельца (D-003, D-016). **Отчёт:** [03_event_history.report.md](03_event_history.report.md).

## Objective

Каждое изменение бизнес-состояния оставляет неизменяемое событие: кто, когда, что именно и в рамках какого запроса. История хранится в PostgreSQL в той же транзакции, что и изменение, и её нельзя переписать. Команды с ключом идемпотентности выполняются ровно один раз.

## Business purpose

Следующий шаг D-002 — одобрения и стоп-кран в пульте (13b). Ему нужны:

- журнал изменений и история за день / неделю / месяц (D-010);
- аудит каждого решения владельца (§2.11);
- гарантия, что повторное нажатие кнопки ✅ не одобрит трату дважды.

Фаза даёт эту основу; интерфейса в Telegram в ней нет.

## Scope

### 1. Контракты (`@roi-dealer/events`)

| Контракт             | Правило                                                                                                                            |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Тип события          | `<entity>.created` для всех 13 сущностей и `<entity>.updated` для 9 изменяемых (22 типа)                                           |
| Конверт события      | `id` (UUID v7), `type`, `aggregate` (`{ type, id }`), `aggregateVersion`, `occurredAt` (UTC), `actor`, `correlationId?`, `payload` |
| `payload`            | Снимок сущности в этой версии; у `updated` ещё `previousStatus`                                                                    |
| Correlation id       | Тот же формат, что в `x-correlation-id` и у бота (`tg-update-<id>`): `[A-Za-z0-9._:-]{1,128}`                                      |
| Ключ идемпотентности | `[A-Za-z0-9._:-]{1,200}`, например `tg-callback-<id>`                                                                              |

### 2. Хранение: миграция `0002_event_history.sql`

- **Таблица `events`:**
  - глобальный порядок `position`;
  - поля конверта;
  - `recorded_at` — время записи по часам БД.
- **Ограничения `events`:**
  - тип соответствует сущности: `created` ⇔ версия 1;
  - `UNIQUE (aggregate_type, aggregate_id, aggregate_version)` — у каждой версии ровно одно событие;
  - `payload` — JSON-объект.
- **Append-only:** `UPDATE`, `DELETE` и `TRUNCATE` событий отклоняются.
- **«Нет изменения без события»:** отложенный constraint trigger на каждой таблице сущностей проверяет при `COMMIT`, что для каждой вставленной или изменённой строки есть событие той же версии. Запись в обход event store — ошибкой или ручным SQL — не зафиксируется.
- **Таблица `idempotency_keys`:** ключ, имя команды, `correlation_id`, время, сохранённый результат. Результат записывается один раз.

### 3. Event store и команды (`@roi-dealer/database`)

- **Репозитории пишут события сами, в той же транзакции:**
  - `insert(entity)` → `<entity>.created`, актор — `createdBy`;
  - `update(entity, actor)` → `<entity>.updated` с предыдущим статусом. Актора передаёт вызывающий: сущность не хранит, кто её изменил.
  - Перед изменением строка блокируется (`SELECT … FOR UPDATE`): предыдущая версия известна точно, а устаревшая версия — `ConcurrencyError`, как в PHASE 02.
- **`database.transaction(work, { correlationId })`:** все события транзакции получают один `correlation_id`.
- **`database.command({ name, idempotencyKey, correlationId }, work)`:**
  - выполняет `work` в транзакции ровно один раз на ключ;
  - повтор, в том числе одновременный, возвращает `{ outcome: 'duplicate', result }` с сохранённым результатом;
  - если `work` упал, ключ не сохраняется, и повтор выполнится заново.
- **Чтение истории:**
  - `events.history(aggregate)` — все версии сущности по порядку;
  - `events.list({ from, to, aggregateType, after, limit })` — события за период с постраничным чтением: основа журнала день / неделя / месяц.
  - Конверт каждого прочитанного события проверяется схемой.

## Out of scope

- Кнопки журнала и истории в Telegram, стоп-кран, одобрения в пульте — 13b.
- Проекции, подписки на события, отправка событий во внешние системы, Temporal — по мере потребности.
- Аудит действий без изменения состояния (просмотры, отказанные попытки) — с PHASE 04 (права).
- Удаление персональных данных из истории (GDPR / CCPA) — вместе с планом PHASE 05; сейчас в событиях нет персональных данных.
- Версионирование схемы `payload`: снимок хранится в форме своего времени; преобразование старых снимков — когда изменится доменная схема.

## Constraints

- Без новых зависимостей.
- Миграция `0001` не меняется; всё новое — в `0002`.
- `@roi-dealer/domain` не меняется.

## Acceptance criteria

1. Каждый `insert` / `update` репозитория создаёт ровно одно событие правильного типа и версии в той же транзакции; откат транзакции убирает и изменение, и событие.
2. Изменение сущности без события (прямой SQL) не фиксируется; событие нельзя изменить, удалить или записать дважды для одной версии.
3. `history` возвращает все версии сущности со снимками, равными сохранённым версиям; `list` возвращает события за период по порядку и постранично.
4. Команда с ключом идемпотентности выполняется один раз, в том числе при одновременных повторах; повтор получает сохранённый результат; упавшая команда не блокирует повтор.
5. Сквозной сценарий DoD v0.1 оставляет полную историю: у каждой сохранённой сущности есть события всех её версий, у решений владельца — актор `owner` и общий `correlation_id` операции.
6. typecheck, lint, format, все тесты, build — зелёные; CI зелёный.
