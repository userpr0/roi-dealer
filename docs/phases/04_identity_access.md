# PHASE 04 — Identity / RBAC / Security

> **Основание:** playbook §7 (PHASE 04 — users, roles, permissions, agent identity, service accounts), конституция §2.3 (permission check перед изменением состояния; AI не меняет permissions), §2.7 (доступы — human gate), §2.11 (least privilege, audit logs); D-004 (сначала только владелец, команда позже); D-018 (одобрение фазы).
> **Требования, отложенные до PHASE 04:**
>
> - аудит действий без изменения состояния: просмотры и отказанные попытки (PHASE 03);
> - права для кнопок 🔎 «Поиск» и ➕ «Добавить» ([план пульта](13_owner_command_center.plan.md));
> - права роли `member` (PHASE 01).
>
> Спецификацию составил Claude (D-018). **Отчёт:** [04_identity_access.report.md](04_identity_access.report.md).

## Objective

У каждого, кто меняет данные системы, есть:

- известная личность;
- роль с минимальными правами;
- возможность мгновенно отозвать доступ.

Проверка прав стоит на единственном пути записи — в репозиториях. Каждый отказ и каждый просмотр пульта попадает в журнал доступа.

## Business purpose

- Со следующих фаз в систему пишут не только владелец:
  - интеграции источников данных (PHASE 05);
  - AI-агенты (PHASE 10);
  - позже команда (D-004).
- До их появления нужно, чтобы:
  - агент не мог принять решение, одобрить трату или выдать себе права (§2.3);
  - новая интеграция получала доступ только после одобрения владельца (§2.7);
  - скомпрометированного агента можно было отключить одной кнопкой.

## Scope

### 1. Роли и права — `@roi-dealer/policies` (был placeholder)

- **Роль — тип актора:** `owner`, `member`, `agent`, `system`, `integration`.
- **Права** — конечный список действий:
  - чтение пульта;
  - запись исследовательских данных;
  - запись Evidence;
  - запросы одобрения;
  - решения;
  - эксперименты;
  - расходы;
  - вклад и вознаграждения;
  - стоп-кран;
  - управление доступом.
- **Матрица «роль → права»** задана в коде (least privilege):
  - `owner` — всё;
  - `agent` — исследование, Evidence, эксперименты (планы), запросы одобрения; никогда: решения, одобрения, стоп-кран, доступы;
  - `integration` — только Evidence и расходы;
  - `system` — автоматические действия: истечение запросов, запуск по одобрению, стоп-кран, предложение доступа; без решений;
  - `member` — исследование, Evidence, запросы одобрения и чтение (команда подключится позже, D-004).
- Для каждой сущности и операции (создание / изменение) определено нужное право.
- `assertPermitted(actor, permission)` — ошибка домена `permission_denied`.

### 2. Личности — сущность `Principal` (15-я)

- Зарегистрированная личность для актора типа `member`, `agent` или `integration`: актор, отображаемое имя, назначение, статус.
- `owner` и `system` встроены:
  - владелец подтверждается каналом (Telegram id из конфигурации);
  - система — это собственные процессы платформы.
- **Жизненный цикл:** `pending` → `active` ⇄ `suspended`; из любого статуса → `revoked` (окончательно).
- **Предложить доступ** может система или владелец (`pending`). Одобрить, приостановить, вернуть и отозвать — только владелец.
- **Писать данные** может только актор с активной личностью. Проверяют:
  - репозиторий — с понятной ошибкой;
  - триггер БД на `events` — последняя линия защиты.

### 3. Доступ выдаёт владелец — через 📥 Решения

- Предложение доступа создаёт личность `pending` и ApprovalRequest нового вида `access_grant` (subject — личность).
- В `/decisions` это обычная карточка. **Одобрить** → личность `active`, **отклонить** → `revoked`; в той же команде, с событиями от `owner`.

### 4. 🔐 Доступы — `/access`

- Список личностей:
  - активные и приостановленные — с кнопками ⏸ «Приостановить», ▶️ «Вернуть», ⛔ «Отозвать»;
  - ожидающие — ссылка на `/decisions`.
- Любое изменение — после подтверждения кнопкой; идемпотентная команда БД, как в 13b.
- **Отказы:** число отклонённых попыток доступа за 7 дней и последняя из них.

### 5. Журнал доступа — `access_log`

- Append-only таблица (не сущность):
  - время;
  - канал (`telegram`, `database`);
  - актор;
  - право;
  - решение `allowed` / `denied`;
  - код причины;
  - `correlation_id`.
- **Что записывается:**
  - каждая команда и кнопка пульта — просмотр или действие владельца (`allowed`);
  - отказ репозитория в записи (`denied`) — сохраняется, даже когда транзакция откатывается;
  - сообщения и нажатия посторонних и из групп (`denied`) — не чаще одной записи на отправителя за 10 минут. Текст сообщений не хранится.
- **В дайджесте** строка «🔐 Отклонённых попыток доступа за сутки: N», если N > 0.

## Out of scope

- **Подключение команды к боту** (роли `member` в Telegram, приглашения) — когда появится команда (D-004).
- **Учётные данные сервисных аккаунтов** (токены API, срок действия) — вместе с первым внешним API-клиентом. Сейчас интеграции работают внутри процессов платформы.
- **Настраиваемая политика одобрений** (порог $20 как настройка) — PHASE 16 вместе с бюджетами.
- **Поиск и добавление данных из пульта** — по плану пульта; права для них уже есть в матрице.
- **Автоматическая приостановка агентов при аномалиях** — с агентами (PHASE 10) и тратами (PHASE 16).

## Constraints

- Без новых зависимостей.
- Решает домен:
  - политики — чистые функции без I/O;
  - БД не хранит матрицу прав, только проверяет активность личности.
- Актор строится только кодом платформы из аутентифицированного канала, никогда из входных данных.
- AI не может менять права (§2.3): управление доступом — только `owner`.

## Acceptance criteria

1. **Матрица прав** покрывает все сущности и операции:
   - владелец может всё;
   - агент не может принимать решения, одобрять, управлять стоп-краном и доступами;
   - интеграция может только Evidence и расходы.
2. **Защита записи:**
   - запись незарегистрированным, приостановленным или отозванным агентом отклоняется репозиторием и БД;
   - запись без права отклоняется;
   - каждый отказ есть в `access_log`, в том числе после отката транзакции.
3. **Предложение доступа:** личность `pending` + карточка в `/decisions`. Одобрение → `active`, отклонение → `revoked`, с событиями от владельца.
4. **`/access`:** приостановка, возврат и отзыв — с подтверждением, один раз; отозванную личность нельзя вернуть.
5. **Журнал доступа:**
   - просмотры пульта и отказы посторонним записываются;
   - повторные попытки одного постороннего ограничены;
   - текст сообщений не хранится.
6. typecheck, lint, format, все тесты, build, сборка образа — зелёные; CI зелёный.
