## Implemented

- **Роли и права — `@roi-dealer/policies`** (был placeholder):
  - 19 прав: просмотры пульта, исследование, Evidence, запросы и решения, эксперименты, расходы, вклад и вознаграждения, стоп-кран, доступы;
  - матрица «роль (тип актора) → права» по принципу least privilege:
    - `owner` — всё;
    - `system` — автоматизации без решений и без управления доступом;
    - `agent` — исследование, Evidence, планы экспериментов, запросы одобрения;
    - `integration` — только Evidence и расходы;
    - `member` — исследование, Evidence, запросы, чтение;
  - право для создания и изменения каждой из 15 сущностей;
  - `decideAccess` — роль + активная личность; `assertPermitted` — ошибка домена `permission_denied`.
- **15-я сущность `Principal`** (`@roi-dealer/domain`):
  - личность агента, интеграции или участника (`owner` и `system` встроены);
  - жизненный цикл: `pending` → `active` ⇄ `suspended`, из любого — `revoked` (окончательно);
  - предлагает система или владелец; выдаёт, приостанавливает, возвращает и отзывает только владелец.
- **Проверка на каждой записи** (`@roi-dealer/database`):
  - перед вставкой и изменением репозиторий проверяет право роли и активную личность;
  - отказ — `DomainError('permission_denied')` с кодом причины, запись в журнал доступа;
  - отказы собираются и записываются после окончания транзакции: запись сохраняется при откате и не ждёт соединение пула, пока текущее занято;
  - репозиторий `principals` с `getByActor`.
- **Защита в БД** (миграция `0004_identity_access`):
  - триггер на `events`: событие (а значит, любая запись) от `member` / `agent` / `integration` без активной личности отклоняется (`ConstraintViolationError`, `kind: 'access_denied'`);
  - актор личности неизменен, отозванная личность не меняется, один актор — одна личность навсегда.
- **Доступ только с одобрения владельца:**
  - `requestAccess` создаёт личность `pending` и запрос нового вида `access_grant`;
  - в `/decisions` это обычная карточка: одобрение делает личность активной, отклонение — отзывает, в той же идемпотентной команде с событиями от `owner`.
- **🔐 `/access`:**
  - активные и приостановленные личности с кнопками ⏸ / ▶️ / ⛔ — после подтверждения, командой с ключом `tg-callback-<id>`;
  - число отклонённых попыток за 7 дней и последняя из них.
- **Журнал доступа `access_log`** (append-only):
  - каждая команда и кнопка пульта проверяет право владельца и записывается (`allowed`) — это аудит просмотров, отложенный из PHASE 03;
  - отказы записи от репозиториев (`denied`, канал `database`);
  - сообщения и нажатия посторонних и из групп — через новый хук роутера `onRejected`, не чаще раза в 10 минут на отправителя, без текста;
  - в дайджесте — строка об отказах за сутки, если они были.

## Security implications

- **§2.3:** AI не может изменить решения, одобрения, стоп-кран и права. Это проверяется трижды: в роли (`@roi-dealer/policies`), в домене (`owner_required`) и в БД (активная личность).
- **§2.7:** доступ новой интеграции или агента — только через одобрение владельца; управление доступом — только владелец.
- **§2.11:**
  - least privilege по ролям;
  - мгновенное отключение скомпрометированной интеграции (`/access` и runbook утечки ключа);
  - журнал доступа: просмотры, отказы, попытки посторонних — без текста сообщений и без значений данных.
- **Актор строится только из аутентифицированного канала** (Telegram id владельца из конфигурации, собственные процессы платформы), не из входных данных (правило в `CLAUDE.md`).
- **Поток попыток посторонних** ограничен одной записью на отправителя за 10 минут (в памяти, до 1 000 отправителей), чтобы журнал нельзя было раздуть.

## Known limitations

- **Команда в боте не работает:** роутер по-прежнему принимает только владельца; роль `member` готова в правах, подключение — когда появится команда (D-004).
- **Учётных данных для сервисных аккаунтов нет** (токены API, срок действия): интеграции работают внутри процессов платформы, их личность задаёт код. Выпуск и ротация — с первым внешним API-клиентом.
- **Роль равна типу актора:** разные права у двух агентов пока не задаются. Понадобится вместе с агентами (PHASE 10), если их полномочия будут различаться.
- **Ограничение записей о посторонних** хранится в памяти процесса; после перезапуска первая попытка записывается снова. Для одной реплики бота этого достаточно.
- **Журнал доступа не показывается построчно** — только число отказов и последний; полный просмотр — вместе с 🔎 «Поиском» (PHASE 13).

## Scope decisions

- **Реализовано:** права на каждой записи, личности и их жизненный цикл, выдача доступа через одобрение, `/access`, журнал доступа с аудитом просмотров (требование, отложенное из PHASE 03).
- **Отложено (Feature Kill Gate, §2.15):**
  - подключение команды к боту и приглашения — когда появится команда (D-004);
  - токены сервисных аккаунтов — с первым внешним API-клиентом;
  - настраиваемый порог одобрений — PHASE 16;
  - автоматическая приостановка агентов — с агентами (PHASE 10) и тратами (PHASE 16);
  - просмотр журнала доступа построчно — с поиском (PHASE 13).
- **Упрощено по сравнению с первой версией спецификации:** приостанавливать доступ может только владелец. Автоматической защиты пока нет, и права системы остаются минимальными; спецификация обновлена.

## Business hypothesis enabled by this phase

- **Безопасный старт сбора данных (PHASE 05) и агентов (PHASE 10).** Каждая интеграция и каждый агент получает доступ только с вашего одобрения, делает только своё и отключается одной кнопкой. Ни агент, ни интеграция не могут принять решение или потратить деньги.
