# 13b — Одобрения, стоп-кран, журнал и дайджест в пульте

> **Основание:** решение владельца D-002 (после PHASE 03 — одобрения и стоп-кран в пульте Telegram), D-009 (дайджест в 10:00 `Europe/Kyiv`), D-010 (журнал и история за день / неделю / месяц), D-006 (human gates), D-017 (одобрение 13b); [план пульта](13_owner_command_center.plan.md); playbook §2.3, §2.7, §2.13.
> Ранний шаг PHASE 13, как 13a. Спецификацию составил Claude (D-017). **Отчёт:** [13b_owner_approvals.report.md](13b_owner_approvals.report.md).

## Objective

Владелец управляет системой из Telegram:

- одобряет или отклоняет запросы кнопками с подтверждением;
- останавливает и возобновляет автоматизации стоп-краном;
- видит журнал и историю за день / неделю / месяц;
- каждое утро получает дайджест.

Каждое действие записывается в PostgreSQL с событием и актором `owner`; повторное нажатие не выполняет действие дважды.

## Business purpose

Гипотеза «владелец управляет системой с телефона» (ROADMAP, уровень 1). Все следующие фазы — агенты, эксперименты, траты — проходят через одобрения владельца (§2.3, §2.7, D-006). 13b даёт этот канал и аварийный тормоз до того, как появятся автоматизации, тратящие деньги.

## Scope

### 1. Бот работает с базой данных

- `DATABASE_URL` у бота необязателен. Без него бот работает как раньше, а команды пульта отвечают, что база не подключена.
- С базой в `/status` появляется проверка `database`, пул закрывается при остановке.
- **Миграции в облаке:** Docker-образ бота содержит миграции и раннер. В Railway их применяет **Pre-deploy Command** до запуска новой версии ([инструкция](../deploy/database.md)).

### 2. 📥 Решения — `/decisions`

- Список ожидающих ApprovalRequest с неистёкшим сроком, ближайший срок — первым. Каждый запрос — отдельная карточка: вид, заголовок, описание, сумма, срок, кнопки **✅ Одобрить** / **❌ Отклонить**.
- **Нажатие → подтверждение:** карточка превращается в вопрос «Одобрить … на $X?» с кнопками **Да** / **Отмена**. Вместе с первым нажатием это двойное подтверждение для денег (план пульта).
- **Подтверждение → `database.command`:**
  - ключ идемпотентности — `tg-callback-<id>`, `correlation_id` — `tg-update-<id>`;
  - запрос загружается из БД, решает домен (`resolveApprovalRequest`, актор `owner`), новая версия сохраняется с событием.
- **Ответы:** истёкший срок, уже принятое решение и одновременное изменение объясняются в карточке, без ошибок и без повторного действия.
- **Кнопки 🔍 «Доисследовать» и ⏸ «Пауза»** относятся к решениям по Opportunity (Decision Engine, PHASE 12) и в 13b не делаются.

### 3. 🛑 Стоп-кран — `/stop [причина]`, `/resume`

- **Новая доменная сущность `SystemControl`** (14-я):
  - ключ `automation`, статусы `running` ⇄ `paused`, причина;
  - остановить может владелец или система (будущая автопауза, D-014 п.10), возобновить — только владелец;
  - изменения идут через репозиторий с событием, как у остальных сущностей.
- **Правило для автоматизаций:** `assertAutomationRunning(control)` — ошибка домена `automation_paused`. Каждая будущая автоматизация и трата проверяет его первым шагом; правило записано в `CLAUDE.md`. В 13b автоматизаций ещё нет, поэтому стоп-кран пока фиксирует решение, показывает его и готов к подключению.
- **Команды:** `/stop` и `/resume` показывают подтверждение с кнопками; подтверждение действует 10 минут.
- **В `/status` и дайджесте:** состояние стоп-крана, кто и когда его включил.

### 4. 🧾 Журнал и 🕘 История — `/journal`, `/history`

- Кнопки **День** / **Неделя** / **Месяц** (24 часа, 7 и 30 дней до текущего момента).
- **Журнал:** все события периода — время по Киеву, кто, что изменилось, например `Opportunity «…»: draft → under_review`.
- **История:** только решения и деньги — решения владельца, одобрения, запуски и итоги экспериментов, расходы, стоп-кран.
- До 30 строк в ответе, дальше — «…и ещё N». Данные только из `events.list` (§2.13).

### 5. 📰 Дайджест — ежедневно в 10:00 `Europe/Kyiv` (D-009)

- **Содержимое:** сколько решений ждёт и ближайший срок; изменения за сутки и сколько из них — действия владельца; расходы, записанные за сутки; состояние стоп-крана.
- **Один раз в день** даже при перезапуске бота: `database.command` с ключом `digest-<дата по Киеву>`.
- **`/digest`** — тот же дайджест по запросу.
- Недельный разбор по понедельникам (D-014 п.12) — вместе с метриками экспериментов (PHASE 13 / 16).

### 6. Код

- **`@roi-dealer/telegram`:**
  - inline-кнопки, `callback_query`, `editMessageText`, `answerCallbackQuery`;
  - роутер принимает нажатия кнопок только от владельца в личном чате;
  - данные кнопки проверяются форматом, текст сообщений не логируется.
- **Новый пакет `@roi-dealer/command-center`:** логика пульта — карточки, подтверждения, стоп-кран, журнал, дайджест, время по Киеву. `apps/bot` только связывает его с Telegram и БД.
- **`@roi-dealer/database`:** `listByStatus(status, { limit })` у изменяемых сущностей; миграция `0003_system_control`.

## Out of scope

- Mini App с данными и проверкой `initData` — позже в PHASE 13.
- Поиск и добавление данных (🔎, ➕), «Спросить систему», бюджеты, эксперименты, статистика, выплаты, риски — по фазам-источникам данных ([план](13_owner_command_center.plan.md)).
- Автопауза при аномальных тратах (D-014 п.10) — когда появятся траты (PHASE 16); стоп-кран готов её принять.
- Создание облачной БД — действие владельца по [инструкции](../deploy/database.md).
- Staging — после первого облачного запуска с БД.

## Constraints

- Без новых зависимостей; часовой пояс — через встроенный `Intl`.
- Бот по-прежнему отвечает только владельцу в личном чате; любое изменение — только после подтверждения; текст сообщений и токен не логируются.
- Решает домен: бот не меняет поля сущностей напрямую.

## Acceptance criteria

1. **Одобрение:** из Telegram — нажатие → подтверждение → запрос `approved` в БД с событием от `owner` и `correlation_id` обновления. Повторная доставка того же нажатия ничего не меняет. Истёкший или уже решённый запрос объясняется без изменения.
2. **Стоп-кран:** `/stop` → подтверждение → `paused` с причиной и событием; `/resume` → `running`. Возобновить может только владелец; `assertAutomationRunning` отклоняет работу на паузе.
3. **Журнал и история:** показывают события периода по Киеву, от старых к новым, с ограничением длины.
4. **Дайджест:** содержит данные из БД, отправляется в 10:00 по Киеву не более одного раза в день, в том числе после перезапуска; расчёт времени верен на переходах на летнее и зимнее время.
5. **Без `DATABASE_URL`** бот работает, команды пульта объясняют, что базы нет.
6. **Образ бота** содержит миграции; команда pre-deploy применяет их к `DATABASE_URL`.
7. typecheck, lint, format, все тесты, build, сборка образа — зелёные; CI зелёный.
