# PHASE 17 — Reward Engine

> **Основание:**
>
> - playbook: PHASE 17 (contributions, rules, verification, calculation, payable state), §11 (DoD ROI CORE v0.1: «record Contribution → prepare Reward calculation»);
> - конституция §2.10 (Reward только за подтверждённый вклад: Contributor → Contribution → Result → Verification → Reward Calculation → Approval → Payable → Paid), §2.3 (решает владелец), §2.13 (суммы считает код), §2.15 (Feature Kill Gate);
> - D-004 (сначала только владелец, команда позже; вознаграждения — PHASE 17), D-006 (выплаты людям — **всегда** с одобрения владельца), D-005 (учёт в USD);
> - план кнопок пульта: «🏆 Выплаты: начисленные вознаграждения; выплата — только двойное подтверждение»;
> - домен PHASE 01: `Contribution` (`recorded` → `verified` / `rejected`, проверяет только владелец), `Reward` (`calculated` → `approved` → `payable` → `paid`, только людям, одобрение `payout`), таблицы `contributions`, `rewards`, `reward_contributions`.
>
> Спецификацию составил Claude (D-020). **Отчёт:** [17_rewards.report.md](17_rewards.report.md).

## Objective

Владелец может вознаградить человека, который помог циклу: привёл клиента, провёл интервью, собрал лендинг. Путь — по §2.10:

1. **Вклад** записан и привязан к результату (тесту).
2. **Владелец подтвердил** вклад.
3. **Сумму считает код** по правилу.
4. **Выплату одобряет владелец** в `/decisions` — второе подтверждение (D-006).
5. **Владелец переводит деньги сам** и отмечает выплату. Она попадает в журнал расходов.

Система ничего не платит сама.

## Business purpose

- **Готовность к команде (D-004):** когда появятся помощники, их вклад и оплата учитываются с первого дня, без таблиц на стороне.
- **Честная экономика:** выплаты людям — расходы категории «Люди» в `/economics` и в ROI системы.
- **Ни одной выплаты без подтверждённого вклада и двух решений владельца** — вознаграждение не уходит по ошибке или «за обещание».

## Scope

### 1. Вклады (`/contribution`)

- **`/contribution <кто> <вид> [тест N] <что сделано>`**, например `/contribution anna продажи тест 1 Привела двух клиентов из своего канала`.
- **Кто** — короткое имя участника латиницей (`anna`, `ivan-k`): буквы, цифры, `-`, `_`, до 32 символов, без персональных данных. Хранится как участник (`member:<имя>`). Владелец себе не начисляет: вознаграждения — для других людей.
- **Вид:** исследование, доказательства, анализ, разработка, контент, продажи, операции, другое.
- **`тест N`** — номер из `/experiments`: результат, к которому относится вклад (§2.10 «Result»). Нужен для правила «% выручки».
- **Подтверждение** «Записать вклад?» → одна идемпотентная команда владельца (`createContribution`, статус `recorded`).

### 2. Проверка вклада

- **В `/rewards`** под каждым вкладом, который ждёт проверки, — кнопки ✅ и ❌.
- **Каждая кнопка спрашивает подтверждение**, затем одна команда владельца: `reviewContribution` → `verified` или `rejected`. Версия в кнопке: устаревшая карточка ничего не меняет.

### 3. Правила и расчёт (`@roi-dealer/rewards`, `/reward`)

- **`/reward <вклады> <сумма>`** — номера вкладов из `/rewards` через запятую и условие. Примеры:
  - `/reward 3 $50` — **фиксированная сумма** (правило `fixed-v1`), до $10 000;
  - `/reward 3,4 10%` — **доля чистой выручки теста** (правило `revenue-share-v1`), 1–50 %.
- **База доли** — подтверждённые оплаты теста за вычетом возвратов, из журналов (как ROI системы). Предзаказы не входят: их могут вернуть. Сумма в центах округляется вниз.
- **Проверки в коде** (§2.10, §2.13):
  - вклады есть и подтверждены;
  - вклады одного человека;
  - вклад не входит в другое действующее начисление;
  - для доли — вклады одного теста и выручка теста больше нуля.

  Не прошло — бот пишет причину, ничего не записывается.

- **Подтверждение** «Начислить anna $50 по правилу …?» → одна команда владельца:
  - `Reward` (`calculated`) с правилом и расчётом в заметке;
  - запрос `payout` в `/decisions` на ту же сумму, на 7 дней.

### 4. Одобрение выплаты (`/decisions`, D-006)

- **Карточка «Выплата»** — обычный запрос с суммой: ✅ → **Да** или ❌ → **Да**. Это второе подтверждение («двойное подтверждение» плана пульта).
- **✅** в той же команде: `approveReward` → `approved` → `markRewardPayable` → `payable`. Деньги к выплате.
- **❌** — `cancelReward`. Вклады снова свободны для нового начисления.
- **Запрос истёк** — начисление остаётся `calculated`. В `/rewards` его можно отменить и начислить заново.

### 5. Выплата (`/paid`)

- **Владелец переводит деньги сам** (платёжные провайдеры — Уровень 3) и пишет `/paid <начисление> <ссылка на перевод>`, например `/paid 2 PayPal 5XY12345`.
- **Подтверждение**, затем одна команда владельца:
  - `markRewardPaid` с датой и ссылкой;
  - `CostEntry` категории `human` на сумму начисления со ссылкой на одобренный запрос `payout`.
- **Расход выплаты не входит в траты теста** и его stop-loss: бюджет теста одобрен отдельно (PHASE 15). В расходах месяца и ROI системы он есть.

### 6. Отмена начисления

- **✖️ в `/rewards`** у начисления `calculated` или `payable` → подтверждение → `cancelReward`.
- **Выплаченное не отменяется.** Ошибку в выплате исправляет сторно расхода — как в PHASE 16.

### 7. Пульт

- **`/rewards` (🏆):**
  - вклады, ждут проверки — с ✅ / ❌;
  - подтверждённые без начисления — с подсказкой `/reward`;
  - начисления: ждут решения, к выплате (с подсказкой `/paid`), истёкшие;
  - выплачено за месяц.
- **Номера** вкладов и начислений — по порядку создания: не меняются.
- **Дайджест:** «🏆 Вклады ждут проверки: N · к выплате: M на $X → /rewards», если есть что делать.
- **Права:**
  - `/rewards` — `history.read`;
  - `/contribution` и кнопки проверки — `contribution.write`;
  - `/reward`, `/paid`, отмена — `reward.write`.

  Всё это есть только у владельца (и у системы).

### 8. База (миграция `0014_rewards`)

**Триггер на `reward_contributions`** — последняя линия защиты §2.10 на уровне базы. Вклад в начислении должен:

- быть подтверждён (`verified`);
- принадлежать тому же человеку, что и начисление;
- не входить в другое действующее (не отменённое) начисление.

Строка вклада блокируется (`FOR UPDATE`): два одновременных начисления одного вклада не пройдут.

## Out of scope

- **Платёжные провайдеры и автоматические выплаты** — Уровень 3. Деньги переводит владелец.
- **Участники в боте** (роль `member` в Telegram, вклады от самих участников) — когда появится команда (D-004). Сейчас вклад записывает владелец.
- **Вклады AI-агентов:** их работа уже учтена в `agent_work` и `agent_runs`, а вознаграждение агентам невозможно (§2.10, только людям). Отдельные записи `Contribution` ничего не добавят (§2.15).
- **Налоги, договоры с участниками, валюты кроме USD** — юридические вопросы Уровня 3.
- **Регулярные выплаты и пулы** (ежемесячная доля, опционы) — когда понадобятся.
- **Mini App и недельный разбор** без вознаграждений: пока нет команды, им нечего показывать (§2.15). Числа — в `/rewards` и `/economics`.

## Acceptance criteria

1. Вклад записывается `/contribution` с подтверждением. Проверяет его только владелец, кнопками с подтверждением.
2. `/reward` считает сумму в коде по одному из двух правил. Неподтверждённый, чужой или уже начисленный вклад отклоняется — в домене и в базе.
3. Начисление создаёт запрос `payout`. ✅ в `/decisions` делает его `payable`, ❌ — отменяет.
4. `/paid` отмечает выплату только у `payable` и пишет расход `human` со ссылкой на одобрение. Расход виден в `/economics`.
5. Все записи — идемпотентные команды владельца с событиями. Повторное нажатие ничего не повторяет.
6. typecheck, lint, format, тесты, build, образы бота, worker и api — зелёные.

## Действия владельца после вливания

- **Новых настроек нет.** Когда появится помощник: `/contribution` → ✅ в `/rewards` → `/reward` → ✅ в `/decisions` → перевод → `/paid`.
