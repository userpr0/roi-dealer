# PHASE 13 — Owner Command Center: план кнопок

> **Статус:** backlog с требованиями владельца (D-010). Реализуется по мере готовности данных: одобрения и стоп-кран — сразу после PHASE 03 (D-002), остальное — по фазам-источникам данных.
> Бот-пульт (транспорт, доступ только владельцу) уже работает — фаза 13a. Стоп-кран, решения (✅ / ❌), журнал, история и дайджест — [13b](13b_owner_approvals.md).

## Принципы

- **Быстрые решения** — inline-кнопки прямо под уведомлением в чате бота. **Подробная статистика и графики** — в Mini App.
- Любая кнопка, меняющая состояние: экран подтверждения с суммой и последствиями; для денег — двойное подтверждение.
- Решение записывается в PostgreSQL и Event History; Telegram — только интерфейс (§2.1).
- Повторное нажатие не выполняет действие дважды (idempotency); у карточки одобрения есть срок действия.
- AI только предлагает; решение принимает владелец (§2.3).
- Ответы на вопросы о фактах (деньги, статусы, количества) — только из БД, с указанием источника (§2.13, §7.3).

## Автопауза при аномальных тратах (D-014 п.10)

- Правило по умолчанию: расход за день **вдвое выше** среднего за последние 7 дней или превышение дневного бюджета → пауза затронутых автоматизаций и экспериментов (как stop-loss) и уведомление в пульт.
- Возобновление — только кнопкой владельца с подтверждением.
- Порог настраивается владельцем; значение по умолчанию — 2× (D-014).
- Реализация: правило — PHASE 13 (пульт) и PHASE 16 (Economics), данные — журнал расходов.

| ------------------------------ | ----------------------------------------------------------------------------------------------- |

| Время от сигнала до решения    | Медиана времени от создания Signal до решения владельца по Opportunity                          |
| Активы цикла                   | Число новых KnowledgeAsset за период (§2.9)                                                     |

## Еженедельный разбор (D-014 п.12)

- По понедельникам в 10:00 `Europe/Kyiv` вместо ежедневного дайджеста приходит недельная сводка (день и время можно изменить).
- Состав: решения за неделю, расходы против лимитов, итоги экспериментов, новые активы знаний, метрики системы.
- В конце — список предложений SCALE / IMPROVE / PIVOT / KILL с кнопками для решения владельца. Предлагает система, решает владелец.
- Цель — около 15 минут в неделю.

## Безопасность поиска и добавления данных

- Только заранее определённые, параметризованные, read-only запросы для поиска; никакого пользовательского SQL.
- Добавление — через те же доменные фабрики и проверки, что и в API (схема → инварианты → политика → запись → событие).
- Каждое действие из Telegram попадает в журнал аудита с `correlation_id`.
