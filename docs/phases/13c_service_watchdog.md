## Objective

Владелец узнаёт о поломке раньше, чем заметит, что система молчит. Бот сам пишет, если:

- `worker` или `api` перестали работать;
- после деплоя сервисы остались на разных версиях;
- провайдер AI не принимает ключ.

Когда проблема уходит, бот тоже пишет. `/status` показывает, что ещё не настроено и где это исправить. Когда всё настроено, бот сообщает об этом один раз.

## Scope

### 1. Отметки сервисов (миграция `0019`, `database.services`)

- **`service_heartbeats`** — по строке на сервис (`bot`, `worker`, `api`): версия, время запуска, время последней отметки и что настроено.
- **Что настроено** хранится только как названия и переключатели, без значений и секретов:
  - `worker` — провайдеры AI, для которых есть ключ;
  - `api` — пульт, форма заявки, оплаты;
  - бот — есть ли адрес `api`.
- **`createServiceHeartbeat`** — отметка сразу при запуске, затем раз в минуту. Сбой записи только логируется и сервис не останавливает.
- **Версия** — `serviceVersion`: `APP_VERSION`, иначе короткий коммит, который развернул Railway (`RAILWAY_GIT_COMMIT_SHA`), иначе `dev`.

### 2. Сторож в боте (`createServiceWatchdog`, `@roi-dealer/command-center`)

Раз в минуту бот читает отметки и журнал вызовов AI. Каждое событие он сообщает один раз и записывает в журнал `service_incidents`. Запись и сообщение делаются одной транзакцией: если сообщение не ушло, ничего не записано, и следующая проверка попробует снова.

| Событие           | Когда                                                                          | Сообщение                                         | Закрывается                          |
| ----------------- | ------------------------------------------------------------------------------ | ------------------------------------------------- | ------------------------------------ |
| Сервис молчит     | Нет отметки `worker` или `api` 10 минут                                        | 🔴 … молчит N мин + где смотреть                  | Новая отметка → 🟢 снова работает    |
| Версии разошлись  | Через 20 минут после запуска бота у сервиса другая версия (у обоих — не `dev`) | ⚠️ Версии разошлись + где смотреть                | Версии совпали → ✅                  |
| Ключ AI не принят | За час есть вызовы с ошибкой доступа (`auth`), после них — ни одного успешного | 🔑 Ключ … не принят + какая переменная у `worker` | Успешный вызов этого провайдера → ✅ |

- **Без действий:** сторож только читает и сообщает. Поэтому он работает и при включённом стоп-кране: тогда владельцу важнее всего знать, что сервисы живы.
- **Сервис, который ещё ни разу не отметился**, не считается упавшим. Об этом говорит чек-лист.

### 3. Чек-лист запуска в `/status` (`setupStatus`)

Строки «🧭 Запуск»: у каждой — ✅ или что сделать и шаг из [`deploy/START.md`](../deploy/START.md).

- `worker` работает (или не запущен, или молчит);
- ключи AI заданы;
- `api` работает;
- форма заявки — есть `PUBLIC_CONTACT_EMAIL`;
- кнопка «Пульт» — у бота есть `PUBLIC_API_URL`;
- доступы решены (или сколько ждут в `/decisions`).

Когда всё готово, остаётся одна строка «всё настроено» с версиями, а бот один раз присылает «✅ Всё настроено».

### 4. Дайджест

Если за сутки сторож о чём-то сообщал, в дайджесте появляется строка «🛠 Сторож за сутки: N (…)» со списком и пометкой «не решено» у открытых.

### 5. Каталог источников

GitHub Issues записан в каталог с вердиктом `rejected` по официальному тексту правил (Acceptable Use Policies §6–7): данные сервиса разрешено использовать только для открытых исследований и архивов.

## Out of scope

- Внешний мониторинг самого бота: бот не может сообщить о собственной остановке. Его перезапускает Railway, а пропавший утренний дайджест заметен владельцу.
- Метрики, трассировка, графики — не нужны при трёх сервисах (§2.15).
- Новые источники Evidence: условия Stack Exchange и Bluesky нельзя прочитать из среды разработки, нужен доступ к их сайтам (D-024).

## Acceptance criteria

1. `worker`, `api` и бот отмечаются при запуске и раз в минуту. Отметка содержит версию и что настроено, без значений и секретов.
2. Молчание сервиса, расхождение версий и непринятый ключ AI сообщаются по одному разу. Окончание каждого — тоже по одному разу.
3. Если сообщение не доставлено, событие не записано и сообщается при следующей проверке.
4. Сторож работает и при включённом стоп-кране.
5. `/status` показывает чек-лист с шагами START.md. «Всё настроено» приходит один раз.
6. Дайджест перечисляет сообщения сторожа за сутки.
7. Тесты: unit и integration на PostgreSQL, процессы бота, `worker` и `api`. `typecheck`, `lint`, `format`, `build` — зелёные.

## Действия владельца

Нет. Сторож начинает работать после вливания PR: сервисы отмечаются сами. Чек-лист в `/status` покажет, что осталось из START.md.
