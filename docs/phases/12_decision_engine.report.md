## Implemented

- **Карточка возможности** (`@roi-dealer/command-center`, `opportunity-cards.ts`) — из БД (§2.13), в пределах одного сообщения Telegram:
  - клиент; проблема → изменение → результат;
  - бизнес-модель и гипотеза цены;
  - оценка PHASE 07 с составляющими;
  - судьи: итог, шесть баллов, слабые места с опасениями;
  - рынок;
  - число цитат и источников, две цитаты со ссылками на оригинал;
  - рекомендация системы с причиной.
- **Рекомендация — правила в домене** (`recommendOpportunity`):
  - неполная оценка → доисследовать;
  - рынок, боль, экономика или риск = 1 → не брать;
  - итог < 40 → не брать;
  - итог ≥ 65 без слабых мест → проверять;
  - иначе → доисследовать.
- **Кнопки ✅ Проверять / ❌ Не брать / 🔍 Доисследовать:**
  - сначала подтверждение, «Назад» возвращает карточку;
  - затем одна идемпотентная команда (`tg-callback-<id>`): `createDecision` от `owner` и `applyOpportunityDecision`;
  - кнопки несут версию возможности: устаревшая карточка ничего не меняет и объясняет почему;
  - право `decision.record`, нажатие — в журнале доступа.
- **Урок решения:** обоснование пишет код — выбор владельца, итог судей, рекомендация, клиент и проблема, по-английски, как остальные данные. Решение находится через `/search`, а судьи получают его как похожий прошлый случай.
- **Карточки приходят сами:**
  - бот каждые 5 минут ищет возможности в `under_review`;
  - каждую версию отправляет один раз — командой с ключом `decision-card-<id>-v<версия>`;
  - неудачная отправка повторяется;
  - стоп-кран останавливает рассылку;
  - `DECISION_CARDS_INTERVAL_MS` в боте.
- **`/decisions`:** после запросов одобрения — «⚖️ Возможностей на решение: N» и до 5 карточек, старые — первыми.
- **Дайджест:** строка «⚖️ Возможностей на решение: N → /decisions».
- **«Доисследовать» без повторов:** судьи оценивают возможность снова, только когда у её болей появились новые сигналы после прошлой оценки.

**Готово «система сама предлагает»:** пост → доказательство → боль → возможность → рынок → судьи → карточка в Telegram → решение владельца.

## Security implications

- **Решает только владелец (§2.7):** `createDecision` требует `owner`; рекомендация системы ничего не меняет.
- **Каждое решение** — подтверждение, затем идемпотентная команда с событием от `owner` (`telegram:<id>`); повторная доставка нажатия ничего не повторяет.
- **Карточка и логи:** в логах — только id и итог решения, без текстов карточки.

## Cost implications

- **$0:** карточки, рекомендация и решения не используют AI.
- **Бот** раз в 5 минут делает один запрос очереди к БД.

## Known limitations

- **Пауза, закрытие и масштабирование** одобренной возможности — с экспериментами (PHASE 15); переходы уже есть в домене.
- **Обоснование решения пишет код;** свободный текст владельца — по запросу.
- **AI-агент знаний,** который ищет закономерности в решениях, — когда решений накопится. Пока урок каждого решения — его обоснование в Company Brain.
- **«Доисследовать»** ждёт новых сигналов от сбора и агента исследований; отдельного поиска именно по этой возможности нет.

## Business hypothesis enabled by this phase

Система сама находит и оценивает возможность и присылает её владельцу. Он принимает решение «проверять / не брать / доисследовать» за минуту, видя доказательства и слабые места. Каждое решение остаётся уроком для следующих оценок.
