# Architecture Decision Records

ADR фиксирует значимое архитектурное решение: контекст, выбор, альтернативы, последствия и способ отката.

## Когда нужен ADR

- выбор или замена технологии, фреймворка, инфраструктурного сервиса;
- изменение канонического стека, конституции или границ между модулями;
- решение, которое дорого откатить (схема данных, формат событий, публичный контракт API);
- любое отклонение от спецификации Phase (§2.12 конституции).

## Процесс

1. Скопировать [`0000-template.md`](0000-template.md) в `NNNN-short-title.md` (следующий свободный номер).
2. Заполнить все разделы; `Status: Proposed`.
3. **Остановиться** и запросить approval владельца. Proposed ADR не даёт права менять архитектуру.
4. После решения владельца: `Status: Accepted` / `Rejected`, заполнить `Approved by` и дату.
5. Отменённое решение не удаляется: новый ADR со ссылкой, у старого — `Status: Superseded by NNNN`.

## Статусы

`Proposed` → `Accepted` | `Rejected` → (`Deprecated` | `Superseded by NNNN`)
