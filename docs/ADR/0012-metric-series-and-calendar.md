# ADR-0012: Ряды чисел спроса и календарь событий

- **Status:** Proposed
- **Date:** 2026-11-03
- **Approved by:** —

## Context

Фаза 05c «Пульс» (этап G, [ADR-0011](0011-closed-loop-with-gen-content.md), D-030) показывает владельцу на 2–6 недель вперёд по рынкам D-008: сезоны, праздники, события и растущие темы. Для этого нужны два вида данных, которых в системе ещё нет:

- **Ряды чисел спроса** — просмотры статей Википедии по дням, позже Google Trends и Keyword Planner. Это не тексты и не цитаты.
- **Календарь праздников и событий** — даты по рынкам из официальных источников.

План 05b оставил это открытым («Решить в спецификации») и требует: смена модели данных — через ADR. Нынешний `Evidence` хранит короткие тексты с цитатами, вычищает персональные данные и отдаётся в извлечение болей (`toSignalDraft`). Число по дню не цитата, вычищать в нём нечего, и в боли оно не превращается — хранить его как `Evidence` исказит обе модели.

## Decision

1. **Журнал `metric_points` — отдельная таблица, не `Evidence`.**
   - Поля: `catalog_key` (источник из `SOURCE_CATALOG`), `series` (ключ ряда, например `wikipedia:en:Tax_return`), `market`, `day` (дата), `value` (число), `collected_at`.
   - Уникальность `(catalog_key, series, day)`: повторный сбор обновляет значение, не плодит строки.
   - Только агрегаты: ни людей, ни событий (как `ai_calls` и `access_log`). Это журнал, не сущность Event History.
2. **Таблица `calendar_events` — праздники, сезоны и регуляторные сроки.**
   - Поля: `market`, `starts_on`, `ends_on` (null для одного дня), `title`, `kind` (`holiday` | `season` | `regulatory`), `catalog_key`, `source_url`.
   - Событие из GDELT или Federal Register остаётся `Evidence` (это текст); календарь на него ссылается, а не копирует.
3. **Все числа считает код (§2.13).** «Рост интереса» — функция домена `interestTrend`: отношение среднего за недавнее окно к базе за прошлые недели. AI в расчёте не участвует.
4. **Сбор — тем же движком, что `Evidence`.** Ряды и календарь собираются путём по образцу `collectEvidence`:
   - первый шаг — `assertAutomationRunning` (стоп-кран);
   - только запись каталога с вердиктом `allowed`;
   - активный principal интеграции (`source:<key>`), доступ которого владелец одобряет в `/decisions`;
   - лимиты из каталога.

## Alternatives

| Вариант                            | Плюсы             | Минусы                                                      | Почему не выбран                       |
| ---------------------------------- | ----------------- | ----------------------------------------------------------- | -------------------------------------- |
| `Evidence` c `kind: 'metric'`      | Без новой таблицы | Ломает смысл `Evidence`: цитаты, вычистку, извлечение болей | Разные данные — разные таблицы         |
| Внешняя time-series БД (InfluxDB…) | Готовые агрегаты  | Новый сервис и стек ради тысяч точек в день; vendor lock-in | PostgreSQL справляется, стек не меняем |
| Хранить только последнее значение  | Меньше строк      | Нельзя посчитать тренд (нужна история по дням)              | Тренд — суть «Пульса»                  |

## Consequences

- **Плюсы.** Модель спроса отделена от модели болей; тренд считается кодом из истории; сбор проходит те же проверки безопасности, что `Evidence`.
- **Минусы.** Две новые таблицы и миграция; новый вид principal-доступа для источников-рядов (но механизм тот же).
- **Границы.** Веса «Пульса» в `scoreOpportunity` — отдельное решение владельца после проверки на примерах (§2.13). ADR только вводит хранение и расчёт.

## Rollback

До миграции — отклонить. После — перестать собирать (стоп-кран и отзыв доступа источника), таблицы остаются с данными или удаляются отдельной миграцией. На `Evidence`, боли и возможности это не влияет: модель спроса отдельная.
