# ADR-0009: Приём оплат — merchant of record Lemon Squeezy, ссылка на оплату и подписанный webhook

- **Status:** Accepted
- **Date:** 2026-10-19
- **Approved by:** владелец, D-022 (Уровень 3: «20b — приём оплат, ADR на merchant of record, провайдера выбирает владелец ключами»). Новых npm-зависимостей нет; абонентской платы нет — провайдер берёт комиссию с продажи. Лимиты D-007 не затрагиваются — остановка не требуется.

## Context

- **Владелец в Украине, покупатели — США, ЕС, Великобритания** (D-008). Продавать напрямую значит самому регистрировать и платить НДС / sales tax в каждой юрисдикции, вести возвраты и споры по картам.
- **Merchant of record** (MoR) продаёт от своего имени: сам берёт налоги, принимает карты, ведёт возвраты и чарджбэки, выплачивает остаток продавцу. На старте это единственный реалистичный путь (D-022).
- **Страницы тестов — без скриптов** (PHASE 19a, 21): строгий CSP `default-src 'none'`. Оформление оплаты не может жить на нашей странице — только переход на страницу провайдера.
- **Тест должен узнать об оплате сам:** выручка — в журнале `revenue_entries` (PHASE 16), шаг воронки `payment` (ADR-0007), возвраты — расходы `refund`.
- **Кандидаты из D-022:**

  | Провайдер     | Оформление без скриптов на нашей странице                                                                 | Привязка оплаты к тесту                                              | Подпись webhook                                        |
  | ------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------ |
  | Lemon Squeezy | Ссылка на оплату (`…lemonsqueezy.com/checkout/buy/<id>`), созданная в кабинете                            | `checkout[custom][…]` в адресе ссылки → `meta.custom_data` в webhook | `X-Signature`: HMAC-SHA256 тела, hex                   |
  | Paddle        | Оформление открывает Paddle.js (скрипт на странице) или транзакция, созданная через API с ключом продавца | `custom_data` транзакции — из Paddle.js или API                      | `Paddle-Signature`: `ts` и `h1`, HMAC-SHA256 `ts:тело` |

## Decision

1. **Провайдер — Lemon Squeezy** (MoR), через **ссылки на оплату**. Владелец создаёт товар и ссылку в кабинете Lemon Squeezy и передаёт её боту (`/checkout <№ теста> <ссылка>`). Система не ходит в API провайдера: ключ API не нужен.
2. **Переход на оплату.** Кнопка страницы теста с методом «предзаказ» (`/l/<slug>/go`) считает клик (`cta_click`) и ведёт `303` на ссылку владельца с `checkout[custom][experiment_id]=<id>` и UTM-источником. Только https и только домен `lemonsqueezy.com`.
3. **Webhook `POST /webhooks/lemonsqueezy` в `apps/api`:**
   - подпись `X-Signature` — HMAC-SHA256 сырого тела с секретом `LEMONSQUEEZY_WEBHOOK_SECRET`, сравнение в постоянное время; иначе `401`;
   - тело до 64 КБ; из него читаются только событие, номер и суммы заказа, режим теста и `custom_data` — имя и почта покупателя не читаются, не хранятся и не логируются;
   - пишет интеграция «Платежи Lemon Squeezy» (`integration:lemonsqueezy`): доступ запрашивает `api`, одобряет владелец в `/decisions`; стоп-кран — `503`, провайдер повторит доставку.
4. **Что записывается:**
   - `order_created`, тестовый режим → оплата теста **проверена** (Release Gate §7.2 «payment flow протестирован»); денег нет;
   - `order_created`, оплачен → `RevenueEntry` (`preorder` для предзаказа, иначе `payment`) на сумму без налога (`total_usd − tax_usd`), 1 клиент, и шаг воронки `payment`, пока тест идёт;
   - `order_refunded` → расход `refund` на прирост суммы возврата (`refunded_amount_usd`), через `recordRefund` (не больше полученного);
   - каждое событие — один раз: журнал `payment_events` (уникальный ключ провайдер + заказ + шаг), всё в одной транзакции.
5. **Права:** интеграции получают `revenue.record`; база дополнительно пускает выручку от интеграции только от `integration:lemonsqueezy` (CHECK). Решения по деньгам по-прежнему за владельцем: система только записывает уже случившиеся оплаты и возвраты.
6. **Paddle** — не сейчас. Его оформление требует скрипта на странице или создания транзакции через API продавца: это новая зависимость и ключ с правом списаний. Добавляется отдельным адаптером, если владелец выберет Paddle (выбор провайдера — ключами, D-022).

## Consequences

- **Плюсы:**
  - налоги, карты, возвраты, чарджбэки и выплаты — на стороне MoR;
  - страницы остаются без скриптов; ссылка на оплату — обычный переход;
  - выручка и возвраты попадают в экономику и воронку сами, без ввода владельцем;
  - ключ с правом списаний в системе не хранится — только секрет подписи webhook.
- **Минусы и риски:**
  - **комиссия MoR** (у Lemon Squeezy — процент плюс фиксированная часть с продажи) не приходит в webhook: в выручке — сумма без налога, комиссию видно в кабинете провайдера;
  - **выплаты в страну владельца** и условия провайдера проверяются при регистрации (ROADMAP §4); владелец принимает их сам;
  - **провайдер может измениться** (условия, владелец компании): адаптер отделён (`@roi-dealer/payments`), замена — новый адаптер и ADR;
  - формат webhook сверен по документации провайдера и примерам; первая настоящая проверка — тестовый платёж в Test mode, без него Release Gate платный предзаказ не выпускает.
- **Владелец:** аккаунт Lemon Squeezy (тестовый режим сразу, боевой — после проверки магазина провайдером), товар и ссылка на оплату для теста, webhook на `<адрес api>/webhooks/lemonsqueezy` с событиями `order_created` и `order_refunded`, секрет — в Variables сервиса `api`. В чат секрет не присылать.

## Alternatives

- **Stripe напрямую** — продавец сам отвечает за налоги во всех юрисдикциях; для владельца из Украины недоступен без иностранного юрлица. Отклонено.
- **Paddle** — см. п. 6: позже, отдельным адаптером.
- **Ручной ввод оплат через `/funnel`** (как сейчас) — остаётся запасным путём, но не проверяет оплату для Release Gate и зависит от внимательности владельца.
